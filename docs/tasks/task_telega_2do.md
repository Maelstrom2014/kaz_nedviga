# Telegram-парсер Алматы: принятые инструкции к внедрению

Адаптация `task_telega_chatgpt.md` (исследование каналов аренды от ChatGPT)
под реальную архитектуру проекта `kaz_nedviga`.

Это **инструкции (не код)** для доработки существующего парсера. Они
сформулированы так, чтобы исполнитель работал в уже принятых в проекте
паттернах и не отклонялся от них без отдельного решения.

---

## 0. Контекст и допущения

### Что уже есть в проекте

- Парсер `TelegramParser` существует и зарегистрирован в `parsers/factory.py`
  (`PARSER_CLASSES`).
- Источник — **публичный веб-превью** `t.me/s/<channel>`. **Без** Telegram API,
  **без** Telethon, **без** токена, **без** клиента. fetch() переиспользует
  антибот-стек `BaseParser` (`curl_cffi`/`requests`, рандомные заголовки,
  SSL/403-ретраи) из `parsers/base.py:343`.
- Парсинг — **только regex и словарная нормализация**, никакого OCR и никакого
  LLM. Это принципиальное ограничение проекта (см. `task_2gis_chatgpt_scrape.md`
  §9 — та же политика) и данного задания.
- Уже извлекаются: цена, комнаты, площадь, этаж/этажность, адрес, телефон,
  фото (из `background-image`-обложек), дата поста. Есть KZ→RU глоссарий
  `_KZ_RU_GLOSS` (`parsers/telegram.py`) для отображения без машинного
  перевода.
- Пропускаются wanted-объявления (`_WANTED_RE`) и посуточные (`_DAILY_RE`).
- Модель данных — единая плоская dataclass `Listing` в `parsers/models.py:63`,
  Поиск результатов идёт в JSON-файл (`app.py:424 _save_results`), а не в БД;
  БД `favorites` (`db.py:18 SCHEMA`) хранит только избранное с оценками/ценами.
- Дедуп сейчас — **только по URL внутри одного прогона** `BaseParser._dedupe`
  (`parsers/base.py:682`) + merge в `app.py:api_search` по ключу
  `f"{source}|{url}"` (`app.py:500`).
- Карта/районы уже есть: `data/districts.py` (список + полигоны JSON),
  тепловая карта `_point_in_polygon` (`app.py:703`), heatmap `app.py:600`.
- Кеш фото SHA1-по-URL в `export_utils.py:22` (`cache/photos/`).
- Pillow уже есть в `requirements.txt` (нужно для perceptual hash).
- Тесты: `tests/test_telegram.py` + фикстура `tests/fixtures/telegram.html`.

### Жёсткие ограничения (из задания и проекта)

1. **Без OCR.** Пункт «OCR с фотографий» (§13 источника) — **исключён**.
   Всю информацию берём из `caption`/текста сообщения и structured-элементов
   превью. Это уже так; просто закрепляем.
2. **Без LLM / без внешних AI-API.** Классификация listing_type, цена-контекст,
   собственник/риелтор, quality-score — **только правила, regex и словари**.
3. **Без перехода на Telethon/Telegram API.** Сохраняем веб-превью.
   Следствие: ограниченная история (~20 постов на страницу, пагинация через
   `?before=`), нет гарантии доступа ко всем каналам. Это учтено ниже.
   ToS-замечание источника (§23/§24) оставляем как есть — проект не строит
   датасет для ML, только classified-агрегатор для личного поиска.

### Что источник предлагает, а проект уже делает — не трогаем

- Захват фото из альбома (делается в `_parse_soup` через `_BG_URL_RE`).
- Пропуск wanted и посуточных (`_WANTED_RE`, `_DAILY_RE`).
- Прайс-нормализация «180к / 300 000 / 300 тыс / теңге / мың» → целое тенге
  (`_extract_price`).
- KZ-лексика → RU для читаемости (`_kz_to_ru`) — не машинный перевод.

## 3. Модель данных `Listing` — расширение

### 3.1. Принцип

`Listing` — общая для всех парсеров, поля с `Optional`/дефолтами. Новые поля
Telegram заполняет то, что извлёк; остальные парсеры оставляют `None` —
как уже делают сегодня.

### 3.2. Поля для добавления (сгруппированы по ролям из §5 источника)

Identity / provenance (некоторые есть, дополняем):

```
listing_type       : Optional[str]   # WHOLE_APARTMENT | PRIVATE_ROOM | SHARED_ROOM | ROOMMATE | SUBLET | HOUSE | SHORT_TERM | WANTED | UNKNOWN (§4)
deal_type          : Optional[str]   # long_term | short_term | unknown
```

Стоимость (§5, §7, §8, §9 источника):

```
deposit            : Optional[int]       # сумма депозита, тенге
deposit_refundable : Optional[bool]      # возвратный?
commission_percent : Optional[int]      # % комиссии (агент)
utilities          : Optional[str]       # "included" | "separate" | "unknown"
utilities_min      : Optional[int]       # напр. 5000
utilities_max      : Optional[int]       # напр. 6000
price_per_person   : Optional[bool]      # цена за человека (подселение)
first_payment      : Optional[int]       # «первый платёж 120к, дальше 80к»
```

Локация 3 уровня (§10 источника):

```
raw_location       уже не нужно — есть address
normalized_location: Optional[str]      # «Толе би / Саина»
residential_complex: Optional[str]      # ЖК
landmark           : Optional[str]      # «возле Сайрана», «рядом с Мегой»
```

`lat`/`lon` уже есть в `Listing`.

Контакт (§14 источника):

```
contact_telegram   : Optional[str]      # @username
contact_whatsapp   : Optional[str]      # нормализованный wa.me
```

`phone` уже есть — привести к нормализованному виду (§8).

Состояние/условия (§5 источника, где реально извлекается **только текстом**):

```
available_from     : Optional[str]       # дата заселения (ISO)
furnished          : Optional[bool]
pets_allowed       : Optional[bool]
children_allowed   : Optional[bool]
owner_probability  : Optional[float]     # 0..1 (§12)
agent_probability  : Optional[float]     # 0..1 = 1 - owner
```

Скоринг/свежесть (§15, §17, §21 источника) — вычисляются post-run:

```
freshness_score    : Optional[float]     # 0..1 (§9)
quality_score      : Optional[int]       # 0..100 (§13)
duplicate_group_id : Optional[str]       # мастер-группа (§10)
```

### 3.3. Влияние на БД избранного

Поиск-результаты идут в JSON (`_save_results`) — новые Optional-поля появляются
там автоматически через `Listing.to_dict()` (`models.py`). БД `favorites`
хранит только избранное. Если хотим сохранять новые поля в избранное —
добавить строки в `_MIGRATIONS` (`db.py:58`) по образцу существующих (текстовые
колонки `TEXT NOT NULL DEFAULT ''`, числа как есть). Решить, какие из
новых полей нужно персистить в «избранное» (предлагаю минимум:
`listing_type`, `deposit`, `utilities`, `owner_probability`, `residential_complex`).

## 4. Классификация `listing_type` и `deal_type` (§6 источника)

### 4.1. Почему критично

Смешивать «целая квартира» и «подселение» — нельзя (источник §6). Сегодня
парсер только **отбрасывает** wanted/посуточные, тип оффера не классифицирует.

### 4.2. Правила (без LLM, словарно)

`listing_type` определяется по ORDERED ключевым словам (первое совпадение
выигрывает). Реестр — в `parsers/telegram.py`, рядом с `_WANTED_RE`.

- `WANTED` — уже есть `_WANTED_RE` (ищу/сниму/куплю/іздеймін/жалдаймын). Сейчас
  такие **пропускаются целиком**. Если хотим их показывать (§4 источника —
  separate `wanted` тип) — это отдельное продуктовое решение; пока
  **оставить пропуск**, но при необходимости классифицировать как WANTED.
- `SHORT_TERM` — уже есть `_DAILY_RE` (посуточн/тәулік/күн). Оставить пропуск.
- `ROOMMATE` — «подселение», «ищем девушку/парня», «нужен сосед/соседка»,
  «возьму девушку/парня», KZ: «қыз керек», «ұл керек», «подселениеге».
- `SUBLET` — «сдаю комнату», «жалу берем» + есть признаки комнаты в целом
  жилье.
- `PRIVATE_ROOM` / `SHARED_ROOM` — «комната», «бөлме» + контекст «в квартире».
- `HOUSE` — «дом», «үй» (внимание: «үй» короткое, высокий риск ложных срабатываний
  — источник сам отмечает «үй» опасным; использовать только с уточняющими
  словами типа «частный дом», «сдается дом»).
- `WHOLE_APARTMENT` — «квартира», «пәтер», «N-комн», «N бөлмелі», «студия».
- `UNKNOWN` — ничего не сработало, но есть оффер-маркер (оставить как есть,
  не дропать — `has_offer_marker` в `_build_listing`).

### 4.3. `deal_type`

- `short_term` — если сработал `_DAILY_RE` (но тогда пост пропускается).
- `long_term` — маркеры «помесячно», «в месяц», «айына», «әр ай», «долгосрочно».
- `unknown` — по умолчанию.

### 4.4. Цена зависит от типа

Это соединяет §4 и §5: для `ROOMMATE`/`SUBLET` цена обычно «за человека», а не
«за квартиру» (§7 источника). См. §5.3.

## 5. Извлечение цены с контекстом (§7, §8, §9 источника)

### 5.1. Главная ошибка, которую нужно избежать

Брать первое число как цену. В одном посте могут быть подряд
`250 000 тг/месяц` (rent), `депозит 250 000`, `комиссия 50%`,
`коммунальные 30 000`. Сегодня `_extract_price` возвращает одно число — этого
недостаточно.

### 5.2. Контекстная классификация чисел

Для каждой числовой находки определять тип по ключевым словам в окне ±40
символов (окно как в текущем «bare number near rent keyword»):

```
PRICE_RENT       — аренда/сда[ёе]т/жалға бер/айына/әр ай/месяц/в месяц/цена/баға/құны
PRICE_DEPOSIT    — депозит/залог/қamsыт/manual KZ «депозит»
PRICE_COMMISSION — комиссия/риелтор/агент/АН/комиссия N%
PRICE_UTILITIES  — коммунал/ком.услуги/коммуналка/коммуналды + KZ «коммуналды»
PRICE_DAILY      — /сут|за сутки|тәулік (→ одновременно SHORT_TERM, пропуск)
```

### 5.3. Итоговая структура (заполняем `Listing`)

```
rent             = PRICE_RENT (привести ×1000 для тыс/мың/к/млн — уже есть логика в _extract_price)
deposit          = PRICE_DEPOSIT
commission_percent = PRICE_COMMISSION (только %)
utilities        = "separate" если найден PRICE_UTILITIES; "included" если «всё включено/коммуналки включены»; иначе "unknown"
utilities_min/max = диапазон «5–6 тыс» → 5000/6000
```

### 5.4. Цена за человека vs за квартиру (§7 источника)

- Если `listing_type in (ROOMMATE, SUBLET)` или рядом «за человека», «с
  человека», «за одного» → `price_per_person=true`.
- Иначе цена за квартиру целиком.

### 5.5. «Первый платёж 120к, дальше 80к» (§9 источника)

Не путать с арендой: `first_payment=120000`, `rent=80000`. Маркер —
«первый», «первый месяц», «заход», «заезд». В `first_payment`, а в `rent` —
второе число.

### 5.6. Депозит `%` (§9 источника)

«депозит 50%» → не сумма, а доля: пометить отдельно, не записывать 0.5 в
`deposit` как число (либо поле `deposit_is_percent=True` — на ваше усмотрение,
но не вписывать в `deposit` float-долю).

### 5.7. Что оставить как есть

Существующий `_extract_price` с диапазоном `30000 <= num <= 200_000_000` —
логику валидации/масштаба перенести в контекстный экстрактор как общий хелпер.

## 6. Адрес и геокодирование (§10, §11 источника)

### 6.1. Три уровня (источник §10)

```
raw:      address (поле уже есть)
normalized: normalized_location  — «Толе би / Саина» из «Толе би-Саина, напротив Asia Park»
geo:      lat, lon (поля уже есть)
```

### 6.2. Нормализация адреса

- Район — через `data/districts.py`: сопоставление по списку районов
  Алматы + `_point_in_polygon` (`app.py:703`) по координатам, если они есть.
- Микрорайон — словарь «Аксай-1/2/3», «Мамыр», «Таугуль» и т.п. (свой словарь
  landmarks, не из внешнего API).
- ЖК — словарь известных ЖК Алматы + regex `ЖК\s+...` / `тұрғын кешен`.
- Landmark — «возле/рядом с/напротив ...»: выкусывать существительное после
  этих предлогов.

### 6.3. 2GIS-ссылки (источник §11) — подарок парсеру

В тексте `/2gis.kz/almaty/geo/...` или `2gis.kz/almaty/firm/...` — извлечь:

```
2gis_url      — исходная ссылка
lat, lon      — если в ссылке закодированы координаты (geo-ссылка содержит их в параметрах)
2gis_object_id — если /firm/<id>
```

Не угадывать адрес из текста, если есть 2GIS-ссылка — координаты из неё
приоритетнее. Реализовать как `_extract_2gis(text) -> dict | None` в
`parsers/telegram.py`.

### 6.4. Грубые адреса (источник §10)

«Саина Шаляпина», «возле Сайрана», «Аксай 3» — нормализовать по словарю
пересечений и микрорайонов; точные координаты без geocoding-сервиса не
получить — оставить `lat/lon=None` и отдавать `normalized_location`.

## 7. Контакты: нормализация (§14 источника)

### 7.1. Телефон

Сейчас `_PHONE_RE` (`parsers/telegram.py:33`) ловит телефон, но сохраняет
сырой формой с пробелами/дефисами. Привести к единому:

```
87071234567 / +7 707 123 45 67 / 8 (707) 123-45-67 / wa.me/77071234567
   → +77071234567
```

Правило: приводить к `+7` + 10 цифр; телефоны не подходящие под формат KZ
отбрасывать (или помечать). Это статическая функция `normalize_phone()`.

### 7.2. WhatsApp

- `wa.me/7707...` / `api.whatsapp.com/send?phone=7707...` → `contact_whatsapp`
  нормализованный.
- Сам номер тоже дублировать в `phone` через `normalize_phone`.

## 8. Свежесть (§17 источника)

### 8.1. `freshness_score`

По часам от `date_published`:

```
0–2 ч      1.00
2–6 ч      0.95
6–12 ч     0.90
12–24 ч    0.80
1–2 дня    0.60
3–7 дней   0.30
7+ дней    0.10
```

### 8.2. Сейчас дата теряется

В `_parse_soup` дата берётся как `str(time[datetime])[:10]` — только YYYY-MM-DD.
Для freshness нужны часы. Сохранять **полный timestamp** (а не [:10]) или
хотя бы час. Поле `date_published` уже есть; расширить формат хранения.

### 8.3. Срочность (boost)

Маркеры «срочно / сегодня / заселение сегодня / освободилась / заехать можно
/ с 1 августа / с завтрашнего дня» → повысить `freshness_score`/`quality_score`.
Реестр маркеров — рядом с существующими `_WANTED_RE`/`_DAILY_RE`.

## 9. Дедупликация (§15, §16 источника) — самый большой пробел

### 9.1. Что не работает сегодня

`BaseParser._dedupe` (`parsers/base.py:682`) дедуплит по URL. Но одно
объявление в трёх каналах = три URL (`t.me/chA/123`, `t.me/chB/456`,
`t.me/chC/789`) → **остаются тремя записями**. Merge в `app.py:500` по
`source|url` не объединяет кросс-канальные дубли.

### 9.2. Правило дедупликации (источник §15)

Счёт похожести:

```
same phone          +0.30
same images         +0.30   (perceptual hash, §11)
same ЖК/normalized   +0.15
same price          +0.10
same rooms          +0.05
similar text (token overlap) +0.10
```

Порог `>= 0.75` → дубли.

### 9.3. Master listing (источник §16)

Не удалять дубль, а группировать. Ввести `duplicate_group_id`. Мастер —
первое по времени появление. Поля для показа/сортировки:

```
sources_count        — сколько источников (источник §16: «3 источника»)
first_seen_at
last_seen_at
sources[]            — список каналов
master_listing_url   — оригинал мастера
```

Реализовать как **post-run pass** в `TelegramParser.run` (сразу после
`self._dedupe`), потому что кросс-канальные дубли живут в рамках одного
прогона telegram-парсера. Для кросс-прогонных дублей — слой merge в
`app.py`, но MVP достаточно within-telegram-run.

### 9.4. «3 источника» как позитивный сигнал

Если объявление опубликовано в 3+ каналах — `quality_score` повысить, не
штрафовать (источник §16: вероятно реальное актуальное предложение).

## 11. Собственник / риелтор (§22 источника)

Сигналы риелтора (RU+KZ):
`комиссия, риелтор, риэлтор, агентство, АН, агент, услуги риелтора, комиссия N%`.

Сигналы собственника:
`я собственник, собственник, сама хозяйка, сам хозяин, без посредников,

Не бинарно: `owner_probability = 0..1`, `agent_probability = 1 - owner`.
Реализуется весовым подсчётом маркеров (каждый сигнал сдвигает вероятность).
Без LLM.

## 12. Quality score (§21 источника) — rule-based 0..100

### Бонусы

```
+20  есть цена
+15  есть точная локация (lat/lon или normalized_location)
+15  есть фото
+10  есть площадь
+10  есть комнаты
+10  есть депозит (поле)
+10  есть условие коммунальных (utilities != unknown)
+5   есть дата заселения
+5   есть контакт
```

### Штрафы

```
-20  подозрение на риелтора (owner_probability низкий)
-20  duplicate (вне мастер-группы, рядовой дубль)
-15  слишком мало информации (нет ни цены, ни адреса, ни фото)
-10  подозрительный текст (только картинка без текста, маркеры спама)
```

Сортировка выдачи — по `quality_score` второй очередью рядом с ценой
(сегодня `app.py:493` сортирует только по цене). Это продуктовое решение —
добавить опцию сортировки по качеству.

### Короткая выдача (источник §21)

Вместо «500 сырых постов» — «N релевантных вариантов», отфильтровав
`quality_score < порог` (порог — в настройках `app.py`/default settings,
как `max_pages`).

## 15. Tiered polling / глубина пагинации (§18, §24 источника)

### 15.1. Тиры источника

```

Tier B — kvartiry222, Arenda_Kvartira_Ala02
Tier C — tn_almaty, kvartiram7, arendakvartiralma
```

### 15.5.2. Как мапить на проект

Проект — on-demand Flask-поиск (`app.py:470`), не фоновый cron. Поэтому
«каждые 5 минут» — не текущий режим. Мапим тир в **глубину `?before=`-батчей**:

```
Tier A — before_batches = 2  (текущая страница + 2 старых)
Tier B — before_batches = 1
Tier C — before_batches = 0  (только свежая страница) или 1
```

Существующий `run` (`parsers/telegram.py:435`) уже делает «1 older batch per
channel» — обобщить до `before_batches` из структуры канала (§1.4). Ограничить
сверху (например 2–3), чтобы не нагружать веб-превью и не ловить блок.

### 15.3. Перерывы

Сохранить текущую паузу `random.uniform(0.3, 0.8)` между батчами; для Tier A
можно чуть увеличить. Политика polite-crawl остается из `BaseParser`.

### 15.4. Запланированный опрос (опц., не MVP)

Если позже нужен фоновый сбор — отдельный шедулер за пределами парсера;
парсер остаётся stateless. В рамках этих инструкций **не реализуем**.
